# 不变量与踩坑清单（改代码前必读）

> 25 条硬约束。每条都对应过一次真实故障或一次返工，改动相关代码前先确认没有违反。
> 其中 2 / 3 / 5 / 17 / 19 / 25 曾导致端到端不可用，最容易反复踩。

1. **包根目录必须叫 `zcode-ide`**（由 `rootProject.name` 决定）。改成别的名字会覆盖参考插件 ZC GUI 的 `intellij-plugin/`，且 ToolWindow id 必须用 `ZCodeIDE`，不能与 ZC GUI 的 `ZCode` 冲突。
2. **端口全 IDE 固定一个**（`ServerProcess.choosePort`，key `zcode.ide.server.port`）。server 是全 IDE 共享的单进程，所有窗口必须同 origin——JCEF 的 `localStorage` 按 origin（scheme://host:port）隔离，端口一变就是全新的存储：草稿、最近使用的模型、界面偏好全部丢失。日志出现 `Reusing ZCode server port` 才正常。旧版按工作区哈希存端口，升级时 `migrateLegacyPort` 只能保住最先启动窗口的旧端口（各项目旧端口是不同 origin，无法合并），其余项目丢一次。IDE 异常退出后残留 server 占着端口时：token 匹配则直接复用（日志 `Reusing ZCode server left by a previous IDE session`；runtime 版本变化由 `ServerProcess` 按 `runtimeVersion` 判定并杀旧进程/换端口，见第 24 条），否则换随机端口。
3. **ToolWindow 不能退化成空状态**：`canCloseContents="false"` + 内容 `isCloseable = false` + 组件级 `CustomShortcutSet` 吞 `Ctrl+W` + `ContentManagerListener` 兜底，四者缺一不可。`Ctrl+W` 在 CEF 层和 Swing 层都收不到，必须在浏览器组件上注册快捷键。
4. **UI 改动一律走 `ideHost=1` 门控**（`packages/ui/src/lib/ideHost.ts` 的 `isIdeHost()`）。桌面端与独立 web 端的行为不能变；否则会破坏官方桌面形态和 e2e。
5. **server 以 local 宿主形态运行**（fork `261fa358`），且**全 IDE 只有一个进程**（`ZCodeServerManager`，应用级）：多个项目窗口共用，项目路径由 webview URL 的 `ideWorkspace` 传入，agent 按 workspaceKey 各自 spawn。生命周期绑定 IDE（首面板懒启动、退出时 `dispose` 停止），关光所有项目也常驻，重开项目秒连。与桌面客户端同身份、会话列表互通；代价是共享 `~/.zcode`，**不要与桌面客户端同时跑**（SQLite 锁冲突）。测试隔离用 `ZCODE_DATA_BASE_DIR` / `ZCODE_DESKTOP_HOME_DIR`。重启 server 会广播重载所有窗口的面板；单个面板坏而 server 活时，重试按钮只重建本窗口（`isServerAlive` 分流）。
6. **`vendor/ZCode` 是 fork 的独立 git 工作副本（真实目录，自带 `.git`），插件仓库对它整体忽略**。fork 的提交/推送都在该目录里执行（`git -C vendor/ZCode ...`），插件仓库只通过 `vendor/zcode.lock` 记录构建用的 commit；重建/搬迁见 `vendor/README.md`。注意它体积大（含 `node_modules`、`dist`），不要误加进插件仓库的暂存区（`git status` 不应出现 `vendor/ZCode` 下的文件）。
7. **路径必须规范化且严格一致**：server 项目根是反斜杠路径，`/api/server-info` 是斜杠；前端消息链接可能是 `./`、`..`。前端先 `normalizeIdeFilePath` 消解，Kotlin 再 `File(path).canonicalFile` 兜底，VFS 找不到要弹通知而不是静默失败。
8. **workspace identity 是很多 bug 的根**：任务行的 `workspace_key` / `workspace_identity` 必须与当前宿主身份一致，否则历史会话点开无反应、归档失败、新对话不沿用最近模型。多窗口共享后 server 不再绑定项目：`ZCODE_SERVER_WORKSPACE` 只注入 `user.home` 作 `/api/server-info` 的默认展示，真实项目路径全靠前端 URL 的 `ideWorkspace`（`main.tsx` 中它**优先于** server-info）；entry-http 的数据修复只以该默认值跑一次性幂等修复，桌面端不受影响。
9. **`runIde` 在本机不可用**：IntelliJ Platform Gradle Plugin 2.1.0 无法解析 IDEA 2025.1 `product-info.json` 中不含 `=` 的 JVM 参数（`Index: 1, Size: 1`）。只能走 zip 安装/替换目录验证。
10. **runtime 解析优先级（5 级）**：`-Dzcode.ide.runtime` → `ZCODE_IDE_RUNTIME` → `<user.dir>/vendor/ZCode` → 插件目录 `runtime/`（完整包）→ `~/.zcode/ide/runtime/current.json` 指向的下载版。开发期打开本工程时，排在前面的是**源码 dist**，不是打包产物；以日志 `web=` 判断本次验证的是哪份前端。全都没有时 `RuntimeProvisioner` 按内置 baseline manifest 下载（第 24 条）。
11. **Node 24 由插件自己保证**（server 使用 `node:sqlite`）。顺序：系统/用户指定的 24（`ZCODE_IDE_NODE` → PATH → 常见目录）→ 用户目录副本 `~/.zcode/ide/runtime-node/v24.*/node.exe`（锁定 baseline manifest 的 `nodeVersion`，不追最新；插件目录旧 `runtime-node` 自动迁移，失败重下）→ 从淘宝镜像（`registry.npmmirror.com`，失败回落 `nodejs.org`）下载、校验 SHA256 后解压安装。下载在后台线程，面板显示进度，首次约 36MB。调试：`ZCODE_IDE_NODE_MIRROR` 换镜像，`ZCODE_IDE_FORCE_NODE_DOWNLOAD=1` 忽略系统 Node（验证插件副本/下载链路）。
12. **数据迁移脚本会写 `~/.zcode`**：`scripts/*.cjs` 默认 dry-run，`--apply` 才执行且会备份。执行前必须关闭桌面客户端和 IDE 插件 server。不要当普通构建脚本反复跑。
13. **`isDesktop` 是形态开关，不是能力探测**。上游约 280 处判断同时控制"本机能力可见"（记忆详情、MCP 用户目录、系统通知、打开文件管理器）和"桌面外壳渲染"（窗口控件、窗口框架、终端、插件市场）。结论：**不伪装桌面**（`isDesktop` 保持 `false`）——窗口控制、托盘、系统通知、自动更新、剪贴板、电源都由 IDE 承担，插件不该补；真正需要的本机数据只有记忆目录（上游写死 `isDesktop`，用 1 行 `isIdeHost()` 门控解决）和 MCP 用户目录（platform 方法，在 `idePlatform.ts` 转发）。细节见 [`IDE-HOST-ADAPTATION.md`](../architecture/IDE-HOST-ADAPTATION.md)。
14. **记忆按 workspace 路径分目录**：`~/.zcode/cli/memories/projects/<slug>-<sha256(小写绝对路径)前16位>/memory`。项目换目录 = 换一套记忆，旧记忆不会自动跟随；迁移目录后要手动合并并合并 `MEMORY.md` 索引，否则表现为"两边记忆没同步"（2026-10-24 `E:\work` → `E:\work` 已处理）。
15. **MCP 本地 workspace 固定走 platform 分支**（`mcpStore.resolveMcpDirectoryService` 对无 identity 的本地 workspace 返回 null）。所以 IDE 的 `idePlatform.ts` **必须实现** `loadMcpFromUserDirectory` / `saveMcpToUserDirectory` 并转发到 `mcpSyncService`；早期返回空 stub 会让「已安装」恒为 0、新建/导入失败。
16. **构建报 `Invalid Character 0..1` 先看文件头**：`od -c` 若全是 `\0`，是文件被写零（曾同时命中 `SettingsPage.tsx` 与 `.git/index`），不是语法错误。恢复：`git show HEAD:<path>` 覆盖文件；`rm -f .git/index && git reset -q` 重建索引。
17. **`JBCefJSQuery` 注入的函数只吃 `{request: string}` 一个对象参数**。直接 `func(jsonString)` 会在 CEF 层抛 `Invalid arguments; expecting a single object`，且错误不会冒到页面（`invoke` 返回的 Promise 只 reject，多数调用点又把它 fire-and-forget），表现为**点击文件/选择目录/打开外部链接全部毫无反应**。所以 `ZCodePanel.injectBridge` 必须包一层：`window.__ZCODE_IDE_QUERY__ = (json) => window['<funcName>']({ request: json })`。2026-10-24 排查「会话里点文件打不开」时发现整条 Web→IDE 桥因此从未生效。
18. **桥方法必须三处同步，未知方法必须报错**：`idePlatform.ts` 声明 → `IdeBridge.dispatch` 分支 → 前端调用点。`dispatch` 的兜底已从返回 `JsonNull` 改成抛 `unsupported bridge method: <name>`；新增能力时不要再改回静默返回。二进制（`ArrayBuffer`/`Uint8Array`）过桥前必须转 base64——`JSON.stringify(new ArrayBuffer(n))` 是 `{}`，`Uint8Array` 会变成数字键对象。IDE→Web 的 `__zcodeIdeMessage` 同理：未知 `op` 打 WARN，不静默丢弃。
19. **同一种用户动作只能有一个判定点**。「点文件怎么打开」这类规则必须收在 `useAppPanels` 的两个汇合点（`handleOpenCodeViewer` / `handleNavigateFileManager`）加 `lib/ideFileOpen.ts`，**不要跟着调用点走**。2026-10-24 曾在变更摘要 ×2、edit 渲染器、内置文件树、摘要辅助 5 个组件里各打一处补丁，覆盖面看似更全，实际是同一个规则被复制了 5 份：后续任何入口新增/改语义都要再找一遍，而且用户一眼就能看出改动发散。判断标准：如果一处改动需要「在 N 个地方保持同步」，先找有没有公共上游（调用链尽头的唯一函数），没有就先造一个再改。
20. **报「功能回归」时先证伪产物，再怀疑代码**。顺序固定为：① `ls -l plugins/zcode-ide/runtime/web/assets/index-*.js` 与 `vendor/ZCode/packages/web-ide/dist/assets/` 对比 hash 是否同一份；② CDP 读页面里 `<script src>` 实际加载的是哪个 hash；③ 再看 jar/源码时间戳；④ 最后才读实现。多窗口共享 server 之后这一点更关键：server 可能被上一次 IDE 会话残留并复用，前端 bundle 与 Kotlin jar 的新旧可以不同步，"代码明明对但行为是旧的"绝大多数是产物问题。同一次排查里，消息链接、预览卡片、变更文件行三条路径实测都正常，说明"多窗口优化破坏了文件打开"这个前提本身不成立——先验证前提能省掉整轮错误的代码修改。
21. **`patch`/`file` 的语义要在宿主侧解释，不要在每个按钮上重复**。内置查看器的 source 类型里，`file`/`patch`/`multi-file-diff`/`text` 都指向真实文件，IDE 宿主统一进编辑器；`media`/`pdf`/`pptx`/`image`/`code-review` 留在内置预览。由此带来一个已知取舍：**「审查」按钮（patch 源）现在也会在 IDE 里打开文件，而不是面板内看 diff**。若要把两者区分开，正确做法是加 `openDiff` 桥方法走 IDE 自带 diff，而不是回到调用点各自判断。
22. **IDE 形态裁剪先问 CSS，能用 CSS 就不要加 `isIdeHost()` 源码门控**。`packages/web-ide/src/styles.css` 只被 IDE 入口加载，写在里面的规则对桌面端与独立 Web 零影响。CSS 可用的判据（满足任一）：目标有 `data-testid`；目标类名/容器名只由单一规则产出（例：`pl-38`/`pl-44` 只由 `resolveTopOverlayLeadingPaddingClass` 产出）；整块容器可按容器名隐藏（例：顶部浮层根节点的 `topoverlayer`）。选择器只能依赖本地化文案（`aria-label` 随语言变）、匿名包装层的随机工具类或长 `:has()` 链时，不要硬凑，改用门控并在变更记录里说明。**隐藏入口必须连带检查占位**：子项 `display:none` 后父容器 padding 仍在（`sidebar-primary-navigation` 的 `py-3`）；隐藏为浮层让位的绝对定位层后，依赖它的 `padding` 仍留白（header / Side Pane tab 栏的 `pl-38`）。2026-10-25 三次返工都源于漏了这一步，完整方法见 [`IDE-UI-TRIMMING.md`](./IDE-UI-TRIMMING.md)。
23. **`workspaceKey` 是字面字符串，必须用 server 的原始 `rootPath`**。server 判定工作区（`shared/src/task-realtime-core.ts` 的 `resolveWorkspaceKey`）就是 `workspaceIdentity?.trim() || workspacePath`，不做任何路径规范化，agent 进程按这个字符串一对一派生。IDE 面板用的是 `projectService` 规范化后的写法（Windows 反斜杠）；远控桥如果把路径转成正斜杠再下发，手机回传后 server 会当成另一个工作区、为同一项目再起一套 agent（2026-10-25 实测：`E:\work\zcode-ide` 与 `E:/work/zcode-ide` 各一套，多占 8 进程 / 930MB）。规则：**归一化只用于比较，不进任何下发字段**；判定点收在 `ide-remote-bridge/src/workspace-keys.ts`，local 目标不要带 `workspaceIdentity`（手机端对 local 会优先拿 identity 当 key）。agent 一项目一个也是官方模型（cwd/会话/项目级 MCP 都绑工作区），不要试图跨项目复用；能省的只有插件宿主与 MCP 子进程（`~/.zcode/cli/config.json`，2026-10-25 已全停）。
24. **薄插件 + runtime 分发的四个硬约束**（方案见 [`RUNTIME-DISTRIBUTION.md`](../build/RUNTIME-DISTRIBUTION.md)，已实施）：① `buildPlugin` 默认薄包（不含 `runtime/`，约 3.8MB），全→薄不 clean 靠 `stripRuntimeFromSandbox` 清沙箱残留——`prepareSandbox` 不清空插件目录，删了这个任务 51MB runtime 会打进"薄包"（实测 5891 条目）；② `src/main/resources/runtime-manifest.json` 只能由 `node scripts/package-runtime.mjs --write-manifest` 生成，`runtimeVersion` 与 `dist/BUILD-INFO.json` 的 fork commit 绑定，手改 baseline = 下载后 sha256 校验必失败；③ runtime 只装 `~/.zcode/ide/runtime/<version>/`，`current.json`/`pending.json` 只能经 `atomicWriteJson`（临时文件 + `ATOMIC_MOVE`）写，只有含 `.complete.json` 的版本目录可被认领；④ zip 解压必须过 `safeEntryTarget`（拒绝绝对路径、盘符、`..`，Windows 反斜杠条目在 Windows 上同样拒绝）——这是远端 zip 的唯一防线，不要"顺手"放宽。
25. **工具窗与启动活动必须声明 `DumbAware`**：平台在 `ToolWindowSetInitializerKt.beanToTask` 里用 `DumbService.isDumbAware(factory)` 决定 `canWorkInDumbMode`；为 false 时 `ToolWindowImpl.createContentManager` 会用 `DumbService.wrapGently` 把整块 content 换成 `DumbUnawareHider`，索引期间只显示 "This view is not available until indexes are built"。启动活动/`ProjectActivity` 同理：非 `DumbAware` 会被压到 smart mode 之后才执行。我们的面板与桥不读索引，**默认全部声明为 dumb-aware**；新增依赖 PSI/索引的桥能力时，要在能力内部自己做 dumb mode 降级，而不是靠"索引完成后再可用"兜底。排查该问题前先确认 Registry `ide.dumb.mode.check.awareness` 是开启状态。
